## 1. System Overview & Problem Statement

Modern e-commerce enterprises face severe **"Data Silo"** challenges caused by fragmented data scattered across static relational databases, real-time web clickstream logs, vendor catalogs, and unstructured invoices. 

This project delivers a **100% automated, serverless ETL (Extract, Transform, Load) pipeline** built on Amazon Web Services (AWS). The system ingests multi-format chaotic data streams, resolves asynchronous race conditions inherent to event-driven architectures, sanitizes engineered data anomalies, and outputs a highly compressed Parquet dataset optimized for business intelligence (BI) analytics.

---

## 2. Multi-Tier S3 Data Lake Architecture

The data lake adheres to AWS S3 best practices by organizing storage into three distinct isolation zones:

```
s3://cws-ecommerce-datalake-sd-9921/
├── raw-zone/          <- Multi-format ingested batch data (CSV, JSON, XML, PDF)
├── processed-zone/    <- Flattened, parsed, and sanitized tabular CSV files
└── curated-zone/      <- Master Snappy-compressed Parquet output for QuickSight BI
```

1. **Raw Zone (`raw-zone/`)**: Acts as the immutable landing area for all incoming data sources.
2. **Processed Zone (`processed-zone/`)**: Stores intermediate parsed CSV datasets produced by Lambda 1.
3. **Curated Zone (`curated-zone/`)**: Contains final consolidated Parquet files generated by Athena CTAS queries.

## 4. Synthetic Data Generation & Engineered Anomalies

To simulate real-world dirty data, the system includes a custom state-machine Python data generator (`src/generator/dataset_generator.py`) that introduces four specific data anomalies:

| File Format | Data Type | Engineered Anomaly | Business Impact / Mitigation |
| :--- | :--- | :--- | :--- |
| **`customers.csv`** | Structured Demographics | **~10% Missing City Values** | Tested SQL imputation using `COALESCE(NULLIF(city, ''), 'Unknown City')` |
| **`products.xml`** | Semi-structured Catalog | **~20% Prices with `$` Symbol** | Tested string cleaning in Lambda 1 & `CAST(price AS DOUBLE)` in Athena |
| **`web_events.json`** | Real-time Clickstream | **~5% Orphaned `GUEST` Users** | Tested funnel record filtering using `WHERE user_id != 'GUEST'` |
| **`receipts.pdf`** | Unstructured Invoices | **~15% Shipping vs Billing Address Mismatches** | Engineered a dynamic `fraud_flag` feature for risk modeling |

## 5. Architectural Shift: Micro-Batch vs Event-Driven Ingestion

### The Concurrency Problem (Check-Then-Act Race Condition)
In pure event-driven pipelines, triggering aggregation functions on every individual `s3:PutObject` event leads to **"Check-Then-Act" race conditions**, where parallel executions overwrite intermediate tables or attempt to query incompletely written batch files.

### The Solution: EventBridge 5-Minute Micro-Batch Model
The architecture decouples ingestion from aggregation:
1. **Event-Driven Parsing (Step A)**: Lambda 1 executes immediately on S3 `PutObject` events to clean individual raw files into `processed-zone/`.
2. **Micro-Batch Master Aggregation (Step B)**: Lambda 2 is scheduled by Amazon EventBridge every 5 minutes. Lambda 2 purges `curated-zone/`, drops prior table metadata, and executes a single master CTAS query.

**Result**: Guarantees **exactly one master Parquet file per batch** and completely eliminates concurrency race conditions.

## 6. Athena SQL Transformation Logic

```sql
CREATE TABLE ecommerce_datalake_db.ecommerce_analytics_master
WITH (
    format = 'PARQUET',
    parquet_compression = 'SNAPPY',
    external_location = 's3://cws-ecommerce-datalake-sd-9921/curated-zone/'
) AS
SELECT
    e.event_id,
    e.timestamp AS event_timestamp,
    e.user_id,
    COALESCE(NULLIF(c.full_name, ''), 'Unknown Customer') AS customer_name,
    c.age AS customer_age,
    COALESCE(NULLIF(c.city, ''), 'Unknown City') AS customer_city,
    c.state AS customer_state,
    c.shipping_address,
    p.product_id,
    p.category AS product_category,
    CAST(p.price AS DOUBLE) AS product_price,
    e.event_type,
    r.order_id,
    r.payment_method,
    r.promo_code,
    r.billing_address,
    CASE 
        WHEN c.shipping_address != r.billing_address THEN 1 
        ELSE 0 
    END AS fraud_flag
FROM processed_zone.events e
LEFT JOIN processed_zone.customers c ON e.user_id = c.user_id
LEFT JOIN processed_zone.products p ON e.product_id = p.product_id
LEFT JOIN processed_zone.receipts r ON e.user_id = r.customer_id AND e.product_id = r.product_id
WHERE e.user_id != 'GUEST';
```
